# Design

## Context

动机见 `proposal.md`。以下是规划阶段的证据，不是修复后的运行结果：

- 仓库 renderer 在点击捕获阶段读取 `more.__VUE__?.[0]`，找不到数组就直接返回；插入以菜单标签去重，并复用现有 preload 重启接口。
- 已安装 LiteLoader 的 `src/renderer/hook.js` 通过代理 `Proxy` 记录组件到 `vnode.el.__VUE__`，并触发挂载、卸载事件。因此只使用该桥接或同一套挂载事件，都不能覆盖 issue 中漏记的组件。
- Issue #1 已确认从可访问的 Vue 根组件向下遍历，可以找到 `vnode.el` 指向“更多”按钮且持有 `ctx.menuItem` 的真实组件；尚未确认桥接漏记的具体原因。
- 现有架构决定要求修改 QQ 菜单数据、由 QQ 负责渲染。现有 C# 测试不覆盖 renderer；插件通过 `build.ps1` 复制进安装器并生成发布压缩包。

## Goals / Non-Goals

**Goals:**

- 以当前按钮和真实菜单能力识别组件，覆盖漏记桥接、多个实例、组件替换和延迟就绪。
- 保持菜单数据注入幂等，重启处理只调用现有 API，不改变会话所有权。
- 组件发现与恢复逻辑留在现有 renderer 文件内，不增加运行时依赖或通用组件框架。

**Non-Goals:**

- 不修补 LiteLoader 全局组件记录机制，不修改第三方插件，不研究与本问题无关的初始化时序。
- 不复制 QQ 菜单 DOM，不接管原生菜单布局或新增菜单入口。

## Decisions

### 1. 按菜单能力匹配，并从真实组件树发现漏记组件

点击捕获阶段先检查当前按钮关联的全部实例。候选必须未卸载、对应当前按钮，并提供包含原生“设置”的菜单数组；不依据数组顺序或组件名称判定。

直接关联实例不能满足条件时，从当前按钮的祖先及页面已记录组件找到可访问根组件，沿真实 Vue 渲染树的组件、子树与子节点关系查找目标；通过访问集合避免重复遍历，不扫描任意对象属性。只接受与当前按钮关联的目标，不修改其他设置菜单。组件发现每次以当前 DOM 为准，不长期持有已经卸载的组件。

这是同一组件定位流程的两个入口，不是在失败后伪造菜单。仅遍历 `__VUE__` 数组仍无法解决桥接完全缺失；只监听 LiteLoader 挂载事件也依赖发生漏记的同一机制，因此不单独采用。

### 2. 保持 QQ 对菜单数据和渲染的所有权

复用现有菜单数组操作和 `refresh` 图标。在原生“设置”之后保持唯一重启项，重绘及数据替换时重新检查当前数组；不依赖旧数组已经处理过的永久标记。保留其他菜单项目和事件处理，不恢复被隐藏的“锁定”“退出账号”。

直接操作弹出菜单 DOM 会绕过 QQ 的渲染、位置计算及事件所有权；现有组件树可访问真实菜单数据，故采用数据注入方式。

### 3. 事件驱动处理组件就绪与替换

保留点击捕获阶段的同步处理，保证可访问菜单在 QQ 打开前完成注入。增加针对“更多”按钮出现、组件替换或弹出菜单生成的 DOM 变化处理，合并同一批变化，只在相关目标出现或改变时重新定位，不使用固定间隔轮询，也不在每次聊天 DOM 变化时扫描整棵组件树。

窗口初始化时处理已经存在的按钮。观察器在渲染窗口销毁时停止，待处理回调不保留脱离页面的节点。若首次点击时组件尚不可访问，由相关 DOM 变化或下一次点击重新处理，不保存永久失败标志。已打开菜单若使用数据快照，至少确保下次打开读取修复后的当前菜单数据；不得通过伪造点击或自动重启刷新界面。

### 4. 不可访问时报告具体错误，不阻断原生菜单

初始化尚未出现主界面不视为错误。用户打开“更多”但无法取得目标组件或原生“设置”时，以带 QQPortable 标识的 `console.error` 报告具体失败原因；连续失败只报告一次，恢复成功后清除失败状态。该错误是 issue 要求的运行错误信息，不输出组件对象、聊天内容或调试跟踪日志。

不捕获和吞掉真正的菜单修改异常。定位失败不阻止 QQ 原来的点击处理，后续仍能重新发现组件。

### 5. 保持现有打包、进程及 DPI 契约

只修改控制插件 renderer；preload、主进程及启动器继续负责现有重启调用链。启动器持有 Windows Job，旧会话完全退出后创建新会话，不新增进程管理者。

运行现有 `build.ps1` 生成内嵌插件副本和发布压缩包，安装器仍为单个 EXE。菜单由 QQ 渲染，使用 QQ 自己的字体、布局及 DPI 处理；在 100%、150%、200% 下实际检查。

## Risks / Trade-offs

- Vue 内部结构并非稳定公开 API → 以 issue 已确认的真实实例和菜单能力为边界；在真实 QQ 中确认组件树遍历路径，结构不可访问时明确报告，不虚构兼容能力。
- 组件树遍历可能昂贵 → 优先当前按钮关联实例，遍历去重，仅在相关 UI 事件执行，避免聊天内容变化触发全树扫描。
- 其他插件可能直接修改菜单 DOM → 使用真实 lite-tools 的两项开关验证全部组合；不将用户报告的关联写成已确认因果。
- DOM 就绪与 Vue 数据更新存在时序差异 → 验证真实组件延迟就绪和菜单重建后的再次打开，不用模拟桥接或假菜单作为验收证据。
- 菜单点击会强制结束会话 → 在独立临时便携目录验证，不操作用户现有会话，不输入或发送聊天消息。

## Migration Plan

用户确认后实现 renderer 修复，通过构建脚本同步安装器内嵌资源和插件压缩包；既有安装的更新仍采用退出 QQ 后覆盖控制插件的既定方式，本任务不自动覆盖用户安装。无需配置或数据库迁移。

完成真实菜单和重启验证后更新架构说明、同步主规格并归档变更。若验证不满足规格，不发布产物；若之后需要撤回，使用上一份完整控制插件包，不保留双实现或兼容别名。
